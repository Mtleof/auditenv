# auditenv — дизайн

## 1. Цель и рамки

Воспроизводимая RL-среда, в которой агент-аудитор по синтетическим записям одной компании за один период
находит четыре типа ошибок и подтверждает каждую доказательствами. Это не продукт для аудита: нет UI,
обучения моделей, реальных данных, сети.

## 2. Версии

| компонент | версия | где |
|---|---|---|
| среда (`ENV_VERSION`) | 1.0.0 | `src/auditenv/__init__.py` |
| схемы (`SCHEMA_VERSION`) | 1.0.0 | там же, `schemas/` |
| генератор (`GENERATOR_VERSION`) | 1.0.0 | там же |
| конфиг (`CONFIG_VERSION`) | 1.0.0 | `generator/config.py` (`DEFAULT_CONFIG`) |
| политика учёта (`policy_version`) | 1.0.0 | `policy.json` каждого эпизода |

Сами конфиги выгружены в `configs/default-1.0.0.json` и `configs/suite-1.0.0.json` (20 конфигов
train/dev с `config_hash`, без seed), история — `configs/CHANGELOG.md`; `tests/test_artifacts.py` падает,
если файлы разошлись с кодом. Версии генератора, схемы, среды и конфига пишутся в `manifest.json`. RNG-ключ эпизода:
`auditenv|<GENERATOR_VERSION>|<seed>|<sha256(canonical config)[:16]>|<attempt>` — изменение любой части даёт
другой эпизод; одинаковые части дают побайтово тот же. Набор train/dev (seed + config) — `evaluation/suite.py`.

## 3. Модель данных и учёта

* Базовая валюта (USD/EUR/GBP/CHF/SEK/JPY; JPY с разрядностью 0), 1–3 иностранные валюты, часовой пояс
  компании с фиксированным смещением, отчётный период — календарный месяц.
* Документы: счета (`invoices.jsonl`, время в поясе контрагента) и платежи (`payments.jsonl`, `invoice_refs`
  с суммами распределения; поле `entity_id` добавлено как расширение). Главная книга (`ledger.csv`) — в базовой
  валюте, время в поясе компании. Курсы (`fx.csv`) — по одному на календарный день, `source → base`,
  decimal-строки; запись курса адресуется ключом `FX:<date>:<src>:<tgt>`.
* Проводки: счёт — Dr 1200 / Cr 4000; платёж — на каждое распределение Dr 1000 / Cr 1200, нераспределённый
  остаток Dr 1000 / Cr 2900; возврат — Dr 1200 / Cr 1000; прочие расходы — Dr 6xxx / Cr 1000.
* Курс берётся на календарную дату документа **в часовом поясе манифеста**; округление ROUND_HALF_EVEN один раз
  на строку. Отсутствующая ссылка — пустое поле CSV / `null` в наблюдении, никогда не угаданная связь.
* Все правила, определения сумм и `affected_ids` для каждого типа вывода публичны (`policy.json`): сложность — в
  анализе, а не в угадывании формата.

## 4. Генератор

Порядок (`generator/__init__.py`, `history.py`, `inject.py`):

1. **Чистая скрытая история**: контрагенты, продукты, курсы (случайное блуждание, курс меняется каждый день),
   счета, планы оплаты, платежи. Ассерты `Builder.assert_clean`: дебет = кредит (глобально и по каждой проводке),
   каждый платёж полностью распределён, нет переплаты счёта, каждый счёт периода проведён ровно один раз,
   строки книги внутри периода, сумма строки = конвертация доли документа по правильному курсу.
2. **Документы и проводки** из истории + шумовые расходы до целевого размера книги (200–2000 строк).
   Документов 20–200.
3. **Внесение ошибок** (каждый тип включается/выключается и имеет счётчик, всего ≤ 12), с записью в
   `provenance.json` (что было, что стало, какие строки добавлены):
   * `duplicate_invoice` — повторный счёт (новые doc_id/invoice_id, те же контрагент/валюта/строки в другом
     порядке, через 30 мин–2 дня), тоже проведён;
   * `missing_or_partial_allocation` — `invoice_refs` платежа пусты либо распределение уменьшено, остаток
     уходит на 2900;
   * `wrong_fx_date_or_rate` — проводки счёта или платежа пересчитаны по курсу соседнего дня или по
     несуществующему курсу (±2–12 %); расхождение ≥ 10 минорных единиц;
   * `period_misattribution` — счёт следующего периода проведён в этом (с «подтянутой» датой или с настоящей).
4. **Взаимодействующие ошибки** (слоты резервируются ещё в чистой истории, ошибка вносится на шаге 3):
   * `fx_partial_boundary` — платёж в иностранной валюте на границе периода (поздний вечер последнего дня при
     отрицательном смещении или ранние часы первого дня при положительном) частично распределён **и** проведён
     по курсу UTC-даты вместо локальной. Две ошибки на одном документе, в разных валютах.
   * `duplicate_cross_period` — счёт конца периода перевыставлен после конца периода (дубль) **и** дубль
     проведён в этом периоде (ошибка периода).
5. **Отвлекающие корректные случаи**: разбитые платежи, законные частичные оплаты (платёж распределён полностью,
   счёт остаётся открытым), один платёж на несколько счетов, возврат (двойная оплата + отрицательный платёж),
   повторяющиеся суммы у одного клиента (разные строки «service week N»), одинаковые строки у другого клиента в тот
   же день, счета на границе часовых поясов (дата «на бумаге» вне периода, в поясе манифеста — внутри),
   счета прошлого периода, оплаченные в этом, счета следующего периода без проводок. Чистые компании — те же
   отвлекающие случаи без ошибок.
6. **Достаточность доказательств**. `validator/` — независимая реализация (свой парсинг CSV/JSONL, своя
   конвертация), работает только по сериализованным открытым файлам:
   * (а) на чистом снимке: схемы, уникальность ID, ссылки, равенства учёта, детектор не находит ничего;
   * (б) после внесения: исчерпывающий детектор находит **ровно** эталонные ошибки (тип, ID, сумма, валюта) и
     никаких «странностей» (непроведённый счёт, несимметричное расхождение и т. п.);
   * (в) для каждого допустимого набора доказательств ошибка выводится заново из **одних только** этих записей.
   Если что-то не сходится, это баг генератора (тесты на 24 + 12·2 seed, плюс негативные тесты на подделку).
   Дополнительно прогнано 400 случайных конфигураций с 63-битными seed, включая крайние (1 клиент,
   0 % и 100 % иностранной валюты, 12 ошибок, 2000 проводок): все сгенерировались и прошли валидатор,
   каждый эпизод создаётся не дольше 0,5 с.
7. **Разнообразие**: валюты, пояса, периоды, размеры, порядок строк (`row_order`), ID — случайные hex;
   `transforms.permute` и `transforms.remap_ids` — метаморфные преобразования для парных проверок.

## 5. Среда

* `reset(seed, config)` создаёт новое состояние эпизода; среда получает от провайдера только `PublicBundle`
  (ровно шесть открытых файлов) и объект `Grader`, у которого вызывает лишь `finalize`.
* Действия — JSON; проверка по схеме (`schemas/`). Неизвестное действие/ID/курсор/плохие аргументы — ошибка из
  фиксированного словаря кодов (без эха ввода и без текста исключений), шаг расходуется.
* Страница ≤ 50 строк (больше — обрезается), курсоры стабильны (`o<offset>`). Калькулятор — свой токенайзер и
  рекурсивный спуск по `Decimal`, без `eval`, лимиты длины/глубины/величины.
* 100 шагов включая submit; 60 секунд (инъецируемые часы для тестов). Превышение ⇒ `truncated`, пустой ответ.
* **Открытый режим**: в терминальном шаге — награда и агрегаты (TP/FP/FN, P/R/F1, экспериментальная метрика).
  **Закрытый режим**: награда всегда 0.0, `info` содержит только счётчики шагов, итог submit всегда
  `{"status": "submitted"}` — даже неверная структура неотличима от верной. Результат — в `provider.log`.
* **Изоляция агента**: в `evaluate` агентские политики работают в отдельном процессе
  (`policies/worker.py`, протокол JSON-строк stdin/stdout, минимальное окружение). Процесс агента получает
  только наблюдения; truth/provenance остаются в памяти процесса оценщика. Oracle воркером запрещён.
  У агента жёсткий дедлайн: если процесс не ответил до конца лимита эпизода, он завершается принудительно,
  и эпизод получает `truncated` с пустым ответом. Упавший агент тоже получает пустой ответ, а прогон
  остальных эпизодов продолжается. Внешние политики подключаются как `модуль:Класс`.
* **Эпизоды с диска**: `DirectoryProvider` читает шесть открытых файлов и `truth.json` из папок, ничего не
  восстанавливая по seed. Поэтому среда работает на файлах, которые третья сторона переупорядочила или
  в которых сменила ID. Тест делает такое преобразование независимым кодом на уровне текста, меняя даже
  формат ID (`INV-7F3A…` → `inv_00012`): на 10 dev-эпизодах награда oracle остаётся 1.0, ответ
  rule_based совпадает, валидатор подтверждает данные.

## 6. Matcher и награда

* Нормализация ID: `strip`, верхний регистр, дедупликация, сортировка. Допуск суммы — 1 минорная единица.
* TP = тип + канонические `affected_ids` + валюта + сумма в допуске + все `evidence_ids` существуют + они
  содержат хотя бы один полный допустимый набор. Сопоставление — максимальное паросочетание (алгоритм Куна,
  детерминированный порядок), поэтому повтор вывода — FP, а неоднозначность не зависит от порядка.
* P, R, F1 по формулам задания (включая крайние случаи). Награда =
  `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`; `inspection_steps` = шаги до submit. Считается в `Fraction`,
  `explanation` не читается. Экспериментальная метрика `partial_credit_f1` (только тип + ID) показывается
  отдельно и в награду не входит.

## 7. Базовые политики и результаты

| политика | что делает | P | R | F1 | return |
|---|---|---|---|---|---|
| random | 3–30 случайных действий (seed 20251121), 0–3 случайных вывода | 0.000 | 0.000 | 0.000 | −0.901 |
| rule_based | читает все таблицы, 4 правила сверки | 1.000 | 0.657 | 0.793 | +0.565 |
| flag_all | обвиняет всё, до 30 выводов | 0.002 | 0.014 | 0.003 | −0.994 |
| oracle | эталон с первым набором доказательств, 0 шагов исследования | 1.000 | 1.000 | 1.000 | +1.000 |

Чистые компании: rule_based F1 = 1 (ни одного ложного обвинения), flag_all = −1. Парные проверки 20/20:
после перестановки и смены ID награда oracle и rule_based не меняется, ответ rule_based совпадает с
точностью до переименования. Максимальное время эпизода ≈ 0.2 с.

## 8. Разбор сбоев

**Пропуски rule_based (20 эпизодов):**

| тип / сценарий | пропущено |
|---|---|
| duplicate_invoice, одиночный | 10 / 13 |
| duplicate_invoice, `duplicate_cross_period` | 4 / 4 |
| wrong_fx_date_or_rate на платеже (одиночный) | 6 / 6 |
| wrong_fx_date_or_rate на платеже, `fx_partial_boundary` | 5 / 5 |
| missing_or_partial_allocation, period_misattribution, FX на счетах | 0 |

Причины соответствуют намеренным упрощениям: дубли ищутся только с одинаковой локальной датой выпуска, а FX
проверяется только по проводкам счетов. Во взаимодействующих сценариях базовая политика находит «видимую»
половину (частичное распределение, ошибку периода) и пропускает вторую — именно это и проверяют сценарии.
Ложных срабатываний нет, в том числе на счетах у границы часовых поясов: политика переводит время в пояс
манифеста. Наивная версия, читающая дату «как написано», давала бы FP на отвлекающих `tz_boundary`.

**random** почти всегда получает −1 на эпизодах с ошибками и ≈ +0.95 на чистых, только когда случайно
отправляет пустой ответ. **flag_all** получила 1 TP за 20 эпизодов (случайно совпавший «пропущенный» платёж,
у которого сумма вывода равна полной сумме платежа) — точность 0.2 %, награда −0.994.

**Ошибки, найденные при разработке:**
наблюдения возвращали ссылки на внутренние записи (агент мог бы их изменить) — заменено на копии, есть тест;
Dockerfile зависел от apt (ради `make`) и PyPI — упал в сборочной песочнице без прокси; теперь проверка
написана на чистом Python (`scripts/check.py`), зависимости ставятся из закреплённых wheel-файлов;
слишком широкий маркер в тесте утечек (`.json"`) срабатывал на публичный список файлов в манифесте — сужен до
приватных путей; воркер при запросе oracle печатал JSON-ошибку вместо завершения — теперь только код выхода 2.

## 9. Честные ограничения

* **Награда не доказывает пригодность для реального аудита.** Данные синтетические, четыре типа ошибок, один
  период, одна компания, упрощённый план счетов, без НДС, начислений, переоценки, курсовых разниц,
  внутригрупповых операций, кредит-нот и мошенничества.
* Достаточность доказательств для FX проверяется в смысле «по этим записям выводится заявленная сумма»; то, что
  других проводок документа нет, следует из полной книги, а не из набора доказательств.
* Изоляция — на уровне процесса: процесс агента не получает эталон, но песочницы файловой системы нет
  (агент с доступом к диску мог бы прочитать `grader/`); дедлайн работает только для агента в отдельном
  процессе — политику, запущенную в одном процессе со средой, остановить нельзя; каталог
  `grader/` в демонстрационном репозитории лежит рядом с эпизодами. В настоящей проверке он должен храниться
  только у оценщика.
* Генератор и сиды публичны: зная код и небольшой seed, можно перебором восстановить эпизод и его эталон.
  Для закрытой проверки нужны секретные 64-битные seed (и при желании секретная соль в RNG-ключе).
* Таблицы небольшие (≤ 2000 строк), поэтому простая политика успевает прочитать всё за ~20–50 шагов; штраф за
  шаги намеренно слабый и различает только равные по F1 ответы.
* Время эпизода зависит от машины; лимит 60 с — проверка «сверху», а не часть детерминированного результата.
* Контейнер: после скачивания базового образа сборка офлайн (wheel-файлы из `vendor/wheels/`, проверка
  sha256, без apt). Проверено: `docker run --network none` проходит всю проверку, траектории
  совпадают с репозиторием побайтово. Базовый образ закреплён тегом, а не digest, поэтому его содержимое
  может немного меняться при пересборке.
